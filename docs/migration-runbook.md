# 다른 업체에서 IM 뉴스룸으로 옮기기: 병행 기간과 전환 날 (팡고링고 → IM 뉴스룸 기준)

대상 예: 청년후계농업신문(chunghyup.com). 기사 약 840건. 옛 서비스를 끄지 않은 채 새 사이트를 먼저 만들어 확인하고, 하루를 정해 도메인만 돌린다.

## 역할

| 누가 | 하는 일 |
|---|---|
| 고객(언론사) | 옛 업체에 자료 요청, 도메인·DNS 계정, 구글·네이버 계정, 새 사이트 확인 |
| 우리 | 가져오기, 새 사이트 꾸미기, 옛 주소 넘기기, 전환 날 점검 |

## 시작 전에 정할 것 (이게 안 정해지면 시작하지 않는다)

- [ ] 옛 업체가 자료를 내주는가: 기사 전체(제목·본문·날짜·기자·섹션)와 원본 사진 파일, 형식은 CSV나 DB 파일
- [ ] 도메인을 어디서 샀고 누가 관리하는가 (DNS를 바꿀 수 있는 사람)
- [ ] 메일을 그 도메인으로 쓰는가 (그렇다면 MX 기록은 건드리지 않는다)
- [ ] 옛 서비스 계약 만료일과 해지 통보 기한
- [ ] 지금 쓰는 기능 중 우리에게 없는 것을 쓰는가: 7개 언어 선택, 독자 회원가입·마이페이지, 포털 FTP 전송
- [ ] 네이버 뉴스 제휴 매체인가 (그렇다면 전송 방식 변경을 네이버 제휴 담당에 미리 알린다)
- [ ] 세금계산서가 꼭 필요한가 (우리는 한국 세금계산서를 발행하지 않는다)

## 병행 기간 (D-14 ~ D-1): 옛 서비스는 그대로 켜 둔다

**D-14 ~ D-10: 자료 받기와 시험 이전**
1. 고객이 옛 업체에서 받은 자료를 우리에게 전달한다 (채팅·메일로 보내지 말고 구글 드라이브 같은 공유 링크로).
2. 새 매체를 만든다. 아직 실제 도메인은 연결하지 않고 체험 주소(미리보기)로만 본다.
3. 섹션을 먼저 만든다: 카테고리 관리에서 옛 사이트와 같은 이름·순서로 정리하고, 구분선이 필요하면 넣는다.
4. 편집국 `관리 → 다른 프로그램 자료 가져오기`에서 기사 파일 → 칸·섹션 맞추기 → 사진 → 가져오기를 한다.
   - 옛 기사 번호가 `legacy_id`로 남는다. 이 번호가 있어야 옛 주소가 새 기사로 넘어간다.
   - 같은 파일로 다시 가져와도 이미 가져온 번호는 건너뛴다. 그래서 전환 날 직전에 새로 쓴 기사만 더 가져올 수 있다.
   - **옛 사이트에서 이미 가져온 기사를 고쳐도 새 사이트에는 자동으로 안 바뀐다.** 고칠 기사는 전환 날 이후 새 편집국에서 고친다.
5. 확인용 SQL (Supabase, 우리 프로젝트): `supabase/data-migration.sql` 맨 아래의 "매체별 옮겨 온 기사 수" 문장. 옛 사이트의 기사 수와 맞는지 본다.

**D-10 ~ D-5: 고객 확인**
- [ ] 기사 수가 옛 사이트와 같은가 (예: 838번까지면 약 840건)
- [ ] 아무 기사 20건을 골라 제목·본문·사진·기자명·날짜가 같은가 (특히 오래된 기사와 사진이 많은 기사)
- [ ] 섹션 이름·순서, 첫 화면 배치, 로고·색
- [ ] 기사 하단 문구, 기자 페이지, 푸터 정보(등록번호, 발행인·편집인, 청소년보호책임자)
- [ ] 광고 배너 위치와 연결 주소 (광고 관리에서 다시 등록)
- [ ] 모바일 화면
- [ ] 고객이 "이대로 전환해도 된다"고 글로 확인 (메일이나 메시지)

**D-5 ~ D-1: 전환 준비**
- [ ] 편집국 계정 만들기와 직원 교육 (기자·편집장 로그인, 기사 쓰기, 승인)
- [ ] 도메인 연결: `매체 사이트 설정 → 도메인`에서 도메인을 넣고 안내된 DNS 값을 받아 둔다 (아직 바꾸지 않는다)
- [ ] **D-2: DNS TTL을 300초(5분)로 낮춘다.** 문제가 생기면 몇 분 안에 되돌리기 위해서다.
- [ ] 구글 서치콘솔·네이버 서치어드바이저 접속 가능한지 확인. 소유 확인이 옛 업체의 HTML 태그라면 **DNS TXT 방식으로 다시 확인**해 둔다.
- [ ] 전환 시간 정하기: 평일 새벽(방문자 적은 때). 금요일과 공휴일 전날은 피한다.
- [ ] 이 작업에 쓸 연락처 서로 교환 (전환 날 바로 연락되는 사람)

## 전환 날 (D-day)

| 순서 | 할 일 | 확인 |
|---|---|---|
| 1 | 마지막 가져오기: 옛 사이트에서 병행 기간에 새로 나온 기사를 받아 같은 방식으로 한 번 더 가져온다 (이미 가져온 건 건너뜀) | 기사 수가 옛 사이트와 같은지 |
| 2 | 옛 사이트에 "전환 중" 안내를 띄운다 (가능하면). 이 시간 이후 옛 사이트에서 새 기사를 쓰지 않는다 | |
| 3 | 고객이 DNS를 바꾼다: `@`(루트)와 `www`의 연결 값을 우리가 알려 준 값으로. **MX·TXT(메일) 기록은 건드리지 않는다** | |
| 4 | 연결이 잡힐 때까지 기다린다 (보통 5~30분). 보안 인증서(https)는 자동 발급 | 브라우저에서 새 사이트가 열리고 자물쇠가 있는지 |
| 5 | **확인 도구 실행** (아래) | 문제 0건 |
| 6 | 서치콘솔·서치어드바이저에 `sitemap.xml`과 `news-sitemap.xml`, `rss.xml` 제출 | 접수 확인 |
| 7 | 네이버 뉴스 제휴 매체면 제휴 담당에 새 전송 주소 통보 | |
| 8 | 기사 하나를 새로 써서 발행하고 첫 화면·검색·모바일에 나오는지 | |
| 9 | 고객에게 "전환 끝" 보고 | |

**확인 도구** (우리 컴퓨터에서, 새 사이트에만 요청을 보낸다. 옛 서비스에는 요청하지 않는다)

```
node scripts/check-migration.mjs --site https://새도메인 --from 1 --to 838 --out 문제목록.txt
```

- 모든 옛 주소(`/ko-kr/articles/번호`)가 새 기사로 영구 이동하고 새 기사가 열리는지, `sitemap.xml`·`news-sitemap.xml`·`rss.xml`·`robots.txt`가 열리는지 본다.
- 전부 보기 전에 일부만 보려면 `--sample 50`을 붙인다.
- 404로 나오는 번호는 "옮기지 않은 기사"이거나 처음부터 없던 번호다. 옛 사이트에서 그 번호가 실제 기사인지 보고, 기사면 자료에서 빠진 것이므로 다시 가져온다.

## 되돌리기 (전환 후 1시간 안에 큰 문제가 생기면)

1. 고객이 DNS를 **옛 값으로 되돌린다** (TTL이 낮아 몇 분 안에 돌아온다).
2. 옛 사이트가 다시 열리는지 확인한다.
3. 원인을 고친 뒤 다른 날 다시 전환한다.

옛 서비스를 아직 해지하지 않았기 때문에 이 되돌리기가 가능하다. **전환 확인이 끝나기 전에는 옛 서비스를 해지하지 않는다.**

## 전환 후 (D+1 ~ D+14)

- [ ] D+1: 서치콘솔 → "색인 > 페이지" 오류, "페이지를 찾을 수 없음(404)"이 급증하지 않는지
- [ ] D+3: 구글에서 `site:도메인`으로 새 기사 주소가 나오기 시작하는지
- [ ] D+7: 네이버 서치어드바이저 수집 오류, RSS 수집 확인
- [ ] 404가 많이 나오는 옛 주소가 있으면 우리에게 알린다 (주소 규칙을 더 넘겨 준다)
- [ ] **D+14 이후, 이상이 없으면 옛 서비스를 해지한다.** 해지 전에 옛 업체에 자료 삭제 요청과 확인서를 받아 둔다.
- [ ] 옛 주소 넘기기(`/ko-kr/...`)는 **최소 1년** 그대로 둔다.

## 알아 둘 점

- 옛 주소와 새 주소가 같은 도메인이면 구글의 "주소 변경" 도구는 필요 없다. 사이트맵 제출과 옛 주소 넘기기로 충분하다.
- 옛 기사 번호가 사라진 기사(삭제된 기사)는 404가 맞다.
- 옛 서비스의 다국어(영어·일본어 등) 주소가 따로 있으면 이 도구가 보는 `/ko-kr/...` 외에 `/en-us/...` 같은 주소는 다른 규칙이 필요하다. 있으면 알려 달라.
